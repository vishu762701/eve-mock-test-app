# EVE Engineering Standard

This is the canonical repository policy. Read it with `SOURCE_OF_TRUTH.md`, the latest owner authorization, live `main`, affected code and exact-SHA CI. Historical reports and old task prompts are evidence, not instructions. An initialization or starter prompt alone does not authorize implementation.

## 0. Owner-instruction fidelity (highest priority)

Sections 0.1 to 0.8 apply to every task. If any other wording in this repository is softer or seems to allow more autonomy, this section wins.

0.1 **Priority.** (1) The latest explicit owner instruction, (2) this file, (3) `SOURCE_OF_TRUTH.md` and `docs/`, (4) historical reports. Never replace an owner instruction with your own design or preference. The only exceptions are the Security and releases rules (section 5): if an instruction would break them, stop, state the exact conflict and wait.

0.2 **Requirement ledger.** Before changing anything, record the owner's outcomes as numbered requirements (R1, R2, ...) in the task checkpoint or execution notes. This is an internal scope check, not a mandatory pause or extra prompt to the owner. Anything not authorized remains out of scope and stays unchanged.

0.3 **No silent deviation.** Do not substitute, simplify, omit, reorder, restyle or "improve" a requested behavior, UI element or flow. Diagnose technical blockers and continue independently on safe, authorized portions; report unmet items with evidence. Pause for a decision only if proceeding requires a new product/UX choice, changes security or data guarantees, expands scope, violates rights, or carries an irreversible production risk. Never claim an unverified requirement is complete.

0.4 **Unclear or wrong instructions.** Do not guess or follow a technically invalid method blindly. Inspect the code, official source and CI, then choose a safe, technically correct implementation within the already authorized outcome and document the reason. Request an owner decision only for unresolved product, license, security, user-data or deployment tradeoffs; continue independent authorized work rather than treating a blocked subtask as a global stop. Record material disagreements in the report.

0.5 **What you may decide alone.** Own technical design, file placement, compatible dependencies, implementation order, repair strategy, tests and build tooling needed for the authorized outcome. Preserve the specified UI, behavior and data contracts. New product features, user-visible deviations, permissions, destructive data changes, license exceptions and production deployment still require explicit owner choice.

0.6 **Continuous source-exact workflow.** For an explicitly authorized Telegram/source-exact feature, run Analysis, Mapping, Implementation and Verification in one continuous task without asking for a second approval. Pin official source and document dependency and license decisions before copying; implement the complete scoped functional subsystem, including integration and tests. Ask only for an unresolved decision under 0.3 or 0.4. Never turn lack of upstream evidence into a fabricated EXACT claim. Details: `docs/telegram-integration-process.md`.

0.7 **Honest wording.** Do not write "exact", "identical", "complete" or "done" unless every requirement in the ledger is verified with evidence. Never claim you read upstream code you did not open; list the files you actually opened. Unopened or unverified material is UNKNOWN, never stated as fact.

0.8 **Final self-check.** Before reporting, re-read the owner's original request line by line and mark each requirement MET, NOT MET or BLOCKED with evidence. Green CI alone is not MET.

## 1. Ownership and scope

Own the complete authorized outcome. Trace affected callers, shared components, Kotlin/Java, resource qualifiers, themes, state, lifecycle, accessibility, persistence, API contracts, backend, authorization, tests and documentation as applicable. Correct root causes and preserve unrelated behavior. No UI/UX choice is permanently locked against a later authorized change, but never change UI/UX that the owner did not request. Delete genuinely obsolete implementation files and orphaned resources when they are proven unused as part of the currently authorized feature; preserve unrelated files, historical migrations and compatibility contracts. Follow section 1A before deleting anything. Do not silently broaden product scope. Escalate product, permission, legal, destructive and production-risk decisions, plus every case under 0.3 and 0.4. Never invent a blocker or conceal one.

## 1A. Permanent production ownership, zero competing implementations and safe dead-code removal

One production responsibility must have one canonical state/mutation/navigation owner. Before adding a class, endpoint, manager, repository, renderer, activity, utility, resource, or persistent state store, search the actual repo for an existing owner and trace real callers across Android, backend, Gradle, Manifest, resources, native/JNI, tests, and docs. Extend the existing owner whenever that preserves the authorized behavior. Do not add parallel implementations, shadow write paths, redundant API clients, duplicate state authorities or competing navigation registrations. Verify changes against the existing registry `docs/PRODUCTION_OWNERSHIP.md` and enforcement suite `.github/scripts/tests/test_production_ownership.py`; update these existing files when ownership genuinely changes. Do not create a second registry or substitute filename heuristics for production-call evidence.

If two paths appear to overlap, prove the actual overlap in production responsibility, writes, callbacks, or navigation before consolidating. Legitimate UI adapters, JNI bridges, source-specific drawables, test fixtures, separate QR payload domains, migration compatibility, and distinct presentation versus authority layers are not duplicates by default. For a proven conflict: choose the surviving canonical owner, migrate every live consumer, preserve external behavior and stored-data compatibility, test the migration, remove the unused implementation and orphaned references, and record evidence in the existing ownership registry. Never delete files merely to inflate a cleanup metric.

For every authorized feature, proactively identify dead files, abandoned helpers, unused drawables, redundant layouts, and obsolete tests directly related to that change. Remove only files proven obsolete after checking references including dynamic/reflection registration, manifest, XML/resource qualifiers, JNI/C++, build configuration, tests, external API compatibility, migration history, licensing and release obligations as applicable. Keep required legacy migrations, attribution notices and supported external contracts. Do not perform unrelated repository-wide cleanup without authorization. Add targeted regression checks so a removed competing owner cannot quietly return.

## 2. Repository and commit policy

Use `main` only: no PR, new branch, force push, destructive reset or history rewrite. There is **no numeric commit ceiling** per feature. Make as many justified, reviewable, coherent commits as the authorized outcome needs; do not manufacture microcommits or documentation-only checkpoints to inflate progress. Multiple independently tested commits may be prepared together and pushed as one ordered fast-forward batch. The batch's final SHA receives exact-SHA FAST CI; never claim intermediate SHAs individually passed when only the batch tip was tested. Keep a concise batch ledger (features, file ownership, commit SHAs, checks, current remote SHA and CI run), not a separate report commit for every step. Fetch and reconcile remote changes before a compare-and-swap push. One main writer at a time, even if independent analysis and local preparation run concurrently.

## 2A. Progressive delivery and honest acceptance

Track each authorized feature in separate dimensions: (1) implementation present, (2) functional/runtime verification, (3) Telegram visual/gesture/physics parity where requested, (4) verified device matrix, and (5) internal APK / legal release eligibility. An OPEN exact-parity claim must not erase completed functional work, and a green build must not be called pixel-perfect. Produce an owner-testable internal debug candidate at meaningful milestones when permitted by source-distribution rights; never weaken release/signing/legal gates to publish it. Prioritize user-visible broken flows and the earliest functional checkpoint before optional refinements, without silently dropping explicit requirements.

## 3. Official-source integration

Official source is required for requested source reuse, not unrelated work. When a named application's source is requested, authenticate its official origin, identify the latest suitable revision at task start and pin the full commit SHA. A prior ZIP is not evidence of latest; verify archive identity, integrity and hashes when used. Check applicable rights, licenses and attribution before copying. If material is unavailable or reuse is not permitted, report the precise limitation and pursue authorized alternatives; never invent code, assets, values or source claims. Telegram's official source is https://github.com/DrKLO/Telegram.

Trace the **minimum complete functional subsystem** from actual entry points and callers through parent classes, resources and qualifiers, drawing and measurement, themes, typography, assets, touch/scroll/velocity, animation/cancellation, state, lifecycle, navigation, insets, clipping, shadows, RTL, accessibility, errors and platform compatibility as relevant. Exclude Telegram account, messaging, authentication, network, credentials and unrelated business logic, and isolate EVE adapters.

Preserve upstream code unchanged. Mechanical adaptations (package names, imports, resource-name collisions, minimal build-compatibility fixes) are allowed and must be recorded. Any visual or behavioral adaptation is classified ADAPTED and must be documented. A new owner decision is required only when it changes the already authorized product scope, visible requirements, security/data protections or licensing/production obligations (0.3–0.5). Do not substitute an unofficial implementation without owner permission.

Record source revision and path/lines or hashes, dependency disposition, EVE integration and actual test/runtime evidence. Classify facts EXACT, ADAPTED, NOT FOUND or BLOCKED; EXACT means the actual upstream implementation is unchanged in the stated scope. Only claim equivalence when the relevant implementation and runtime behavior are verified. Follow `docs/telegram-integration-process.md` and `THIRD_PARTY_NOTICES.md` for practical provenance and release obligations; a byte match or green build alone does not establish parity or legal clearance.

## 4. Verification and recovery

Run focused local checks on changed production paths first: positive/negative/error cases, lifecycle, account ownership, persistence, Day/Night themes, RTL, font scaling, navigation modes, accessibility, motion, cancellation and relevant shared callers. Preserve meaningful JVM, Rust, Android and backend tests. Static text-contract tests are supplemental, not a replacement for executable behavioral tests.

Each **pushed fast-forward batch** needs an exact-SHA FAST CI on its final SHA. To avoid idle time, independently prepare up to three nonoverlapping authorized workstreams while the submitted batch runs. Never push from two writers concurrently, overlap shared state ownership, or overwrite an in-flight change. Multiple reviewed commits may ship in one ordered batch; follow the current remote head and reconcile before any next push. If FAST goes red, fix its first actionable failure before pushing another unrelated batch. A failing FULL emulator gate blocks release acceptance but does not invalidate an independently green FAST build or prohibit separate prepared work; distinguish functional and infrastructure failures clearly.

Use a **bounded failure loop**. First classify: source/compile, test assertion, Android emulator/ADB/GPU infrastructure, or missing device/rights evidence. For a reproducible app/test failure, change the root cause and rerun its smallest reliable test before broader CI. For an emulator guest loss with no JUnit assertion, capture guest/host evidence; at most one same-SHA infrastructure retry is justified, and repeated failures require a new diagnosis or environment change, not another blind `[eve-full]` push. Reserve `[eve-full]` for a real release-candidate gate, or use manual FULL dispatch. FAST must not disguise red tests; FULL must exercise both navigation modes without test exclusions, with APK checksum and explicit publication approval. Tests and release safeguards never become optional merely to shorten a build.

## 4A. Efficient CI diagnostics

Fail fast on deterministic governance/source-contract errors before expensive SDK/native setup. Preserve the original failing exit code and show the first actionable compiler/test error. Report emulator/ADB disconnects and absent JUnit evidence as infrastructure **suspicions**, not proven application defects. Keep bounded timeouts, cancellation cleanup and captured diagnostics on test failures. Prefer existing pinned toolchains/caches and independent test shards over repeatedly changing GPU flags without new evidence. Measure build durations and failures by stage before tuning timeouts or resources.

## 5. Security and releases

Preserve Firebase identity and access control, admin authorization, server-authoritative scoring, answer confidentiality, account isolation, D1 migrations, API compatibility, secrets, signing, licensing and user data. For cross-layer work trace real Android requests through Worker authentication/validation, D1 and Firebase where relevant; test actual handlers and compatibility. Backend commits may be staged on `main`; live Worker deployment and remote migrations require separate explicit owner authorization and the manual production workflow. Do not weaken safeguards for speed.

## 6. Continuity and reporting

Work while a supported session or cloud task is actually active; never promise background execution without evidence. At a real interruption record current SHA, completed work, in-flight lanes with file ownership and tests, exact-SHA run/job conclusions, first failure and push-gate status, remaining requirements and next action. Do not create checkpoint-only commits after every successful code change. Report VERIFIED, INFERRED and UNKNOWN separately with evidence. Identify related out-of-scope defects by impact without silently fixing them.

Keep routine batch reports concise: changed behaviors, meaningful test evidence, exact-SHA CI status and blockers. At a terminal milestone, provide the requirement ledger (implementation vs acceptance status kept separate), source-exact parity table for touched components, actual native/device evidence, release rights and outstanding decisions. Never claim an unverified screen complete.
