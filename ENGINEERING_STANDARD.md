# EVE Engineering Standard — lean execution policy

This is the single workflow policy. The latest explicit owner request defines scope; SOURCE_OF_TRUTH.md describes architecture and permanent security/data boundaries. Historical mission prompts, audit reports, checkpoint files and templates are not execution mandates.

## 1. Execute the owner's actual outcome
- Implement authorized results end-to-end, including impacted Android resources, Day/Night, RTL, accessibility, state, backend and tests as relevant. Decide routine engineering details independently. Do not stop for repeated approvals or finish with an audit-only report.
- Preserve unrelated working behavior. Do not invent requirements, "EXACT" fidelity, CI results or background execution. For changed files, use actual code/test evidence. Report uncertainty as UNKNOWN and blocked external acceptance as BLOCKED; continue independent work.
- No mandatory per-feature R1–R99 document, heavyweight ledger, duplicate source map, audit-only milestone or checkpoint-only commit. Keep a short working task list internally. At a real interruption, save one concise resume record with HEAD, local work, failing gate and next action.
- Search for the existing owner of affected production state, navigation or mutations before introducing another. Remove proven obsolete code/resources with caller and compatibility checks. Keep required migrations, licenses and public contracts.
- Mark implementation present separately from functional, visual/gesture, device and release acceptance. A green build does not prove exact UI/UX. A lack of physical hardware is not a reason to stop unrelated coding.

## 2. Fast source and review decisions
- Use official Telegram source when the requested outcome depends on Telegram source. Authenticate the revision, pin its full commit SHA, and inspect the minimum complete functional subsystem (including required resources, callers and motion). Do not repeat source authentication for ordinary EVE fixes.
- Reuse verified upstream atoms where lawful. Classify source claims EXACT, ADAPTED, NOT FOUND or BLOCKED with concrete provenance. An adapter is not unchanged upstream code. Do not import Telegram account credentials, messaging, network or unrelated services.
- Preserve relevant attribution, third-party notices and license evidence. Avoid duplicate documentation; update the existing source/ownership record only when its facts materially change.

## 3. Commit, build and delivery
- Protected main with pull-request integration or authorized fast-forward batch, one writer. There is no numeric commit ceiling. No force push, destructive resets or history rewrite. Batch related implementation and test fixes into coherent commits; do not create a new checkpoint/report commit after every task. Reconcile remote main before push.
- Run smallest relevant local tests first. Each pushed implementation batch must pass exact-SHA FAST CI on its final SHA. Diagnose first real error and repair forward; do not re-run the same failing build repeatedly without a cause. Treat emulator/ADB/GPU infrastructure errors separately from application test failures.
- FULL native emulator testing is a final integrated-candidate gate, not a tax on small commits. Test both gesture and three-button navigation and verify built APK SHA-256. Publish an APK only through a separately authorized and license-cleared delivery path; never describe an unavailable artifact as delivered.
- Do not run expensive Gradle/NDK/emulator builds on a phone by default when equivalent hosted CI is available. Keep Termux work to source operations and lightweight checks unless the owner explicitly chooses a phone build.

## 4. Security and release protections
- Keep Firebase identity, Worker/D1 admin authority, answer secrecy, server-side scoring, account isolation, data compatibility, signing and secrets protected. Test relevant production request/response paths when modifying them.
- Live Worker deployment, remote D1 migrations, destructive production data changes, public APK distribution and licensing exceptions require separate explicit owner authorization. Keep release compliance gates and manual production workflow intact. Do not bypass tests or permissions to force a green check.
- If a real owner-only product, security, data or legal decision is required, state the exact blocker and keep progressing on unrelated authorized work.

## 5. Minimal reporting
- During execution: report only material failures or decisions. At delivery: changed behavior, exact commit SHA, relevant tests/FAST/FULL results, APK access and unresolved external blockers. Do not keep re-reading or rewriting multi-thousand-line mission reports for ordinary fixes.

## Development-only fast-build mode
- The owner is developing a private app and may change any UI/UX behavior. No UI/UX choice is permanently locked. Own the complete authorized outcome, but not unrelated work. Do not silently broaden product scope.
- Remove only files proven obsolete. For a source-exact request, authenticate its official origin and record path/lines or hashes plus runtime behavior where available. Do not substitute an unofficial implementation without owner permission. Proceed within the authorized scope without asking for a second approval.
- On ordinary main pushes, only compile the debug APK. Do not automatically run Gradle unit tests, AndroidTest, lint, Rust tests, Python/CI contract suites, documentation checks, backend/Firebase tests, source acceptance audits, visual gallery or gesture/three-button emulators. All of these run only when the owner triggers manual FULL via GitHub Actions workflow_dispatch.
- Keep the manual FULL and release/security protections available and truthful. A fast compilation pass means BUILDABLE only, not TESTED or VERIFIED. Extra non-build GitHub workflows for documentation, dependency evidence and source imports are manually dispatched.
- The normal quick build cannot promise a fixed wall-clock time: compilation, NDK, Gradle caches and runner availability vary. Prefer cached cloud builds over phone builds.

- Automatic FAST is ARM64-only for rapid Android development; manual FULL builds all four native ABIs and exercises both emulator navigation modes. Do not describe ARM64-only FAST as a universal APK or as complete app verification.

## 6. Continuous app-wide implementation loop (owner-authorized)
- The currently authorized mission is a full EVE UI/UX and functionality rebuild using source-verified Telegram Android primitives. Treat earlier feature/checkpoint reports as history, not a completed acceptance list. Inspect live code and record only the next few actionable gaps; do not restart previously integrated components without a defect.
- Source order: use the owner's phone-storage `Telegrammaster.zip` first, verify its SHA-256 and official revision; use an authenticated pinned `https://github.com/DrKLO/Telegram` checkout if the archive is inaccessible/invalid. Reuse the extracted verified source between batches. If the ZIP has already been authenticated this session, do not spend another batch rediscovering it.
- Run the active loop in one supported agent execution: select the highest-impact uncompleted code task; inspect original Telegram source and affected EVE production paths; implement the complete EVE flow and its real UI components, lifecycle and state; run focused local checks; make coherent main-only commits; check exact-SHA compile-only FAST; fix failures; then IMMEDIATELY start the next outstanding implementation task without ending the execution or waiting for another user message.
- Explicit priorities: broken polls/votes, banners/media/CRUD, repeated reloads/flicker, nonfunctional actions, wrong popup or bottom-sheet geometry/entry/animation, wrong selection checkmarks, profile/QR, exams/results, admin screens, notifications, settings, and finally proven dead/duplicate code. Inspect all registered Activities plus Fragments, adapters, custom views, dialogs and shared resources. Preserve backend security and current user data.
- Prohibit milestone-as-completion: a source verification, successful push, green FAST, first P0/P1 batch, good summary, or docs-only checkpoint never ends the mission while actionable code remains. Do NOT commit giant checkpoint reports during normal batches. Send a brief factual progress note only when useful; it must not replace the next code change. Do not waste time re-reading or appending to the historical 3,000+-line checkpoint.
- Stop only when (a) all independently actionable authorized implementation tasks are complete and evidenced, (b) the owner explicitly stops, (c) an actual session/tool/time/permission limit prevents further tool use, or (d) no independent safe work remains because of genuine external dependencies. For (c) and (d), record a SHORT restartable handoff with exact HEAD, uncommitted work, first remaining code task, source path, current CI run and blocker. A session ending is not background execution; never claim autonomous work will continue after termination.
- Android CI policy remains: ordinary push = ARM64 compile only; exhaustive FULL, lint, unit suites, both emulator navigation modes and visual comparisons only on explicit owner instruction. Local focused code checks may be used for defects, without triggering whole-app FULL. Do not falsify EXACT source parity where Telegram has no equivalent behavior; compose verified primitives for EVE-only features.
